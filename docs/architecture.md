# Архитектура IT-ВЕЧЕ

## Модель состояний

```
Сессия:  draft ──(первый тур открыт)──► active ──(решение зафиксировано)──► decided
             └──────────── «Новая сессия» переводит прежнюю реальную сессию в archived ─────────┘

Тур:     open ──(Завершить)──► closed ──(Показать результаты)──► published
                               │ outcome вычисляется сервером в момент закрытия
```

Следующий шаг организатора всегда вычисляет сервер (`nextStep`), а не клиент:

| Итог последнего опубликованного тура | Следующий шаг |
|---|---|
| нет туров | `start_main` — «Начать голосование» |
| `winner` (> 50% в первом туре или больше голосов во втором) | `decide` — «Зафиксировать решение» (`method = vote`) |
| `runoff` (нет большинства, два лидера определены) | новый тур `runoff` с двумя финалистами |
| `tiebreak` (равенство мешает определить финалистов) | новый тур `tiebreak` среди претендентов. Уже прошедшие финалисты переносятся в `carried` |
| `tie` (равенство во втором туре или при переголосовании) | «Переголосовать» (тур `revote`) или решение ГД (`method = ceo`) |
| `no_votes` | «Повторить тур» |

Правила реализованы чистыми функциями в `shared/decision.ts` и покрыты тестами `server/test/decision.test.ts`. Проценты считаются методом наибольшего остатка, поэтому их сумма ровно 100.

## Схема БД

`server/src/migrations/{sqlite,postgres}/001_init.sql`:

- `options`: три варианта, заполняются из `shared/options.ts`.
- `voting_sessions` (`id, slug, title, status, is_demo, access_mode, expected_participants, created_at`).
- `voting_rounds` (`id, session_id → sessions, number, type, status, eligible_option_ids, slots, carried_option_ids, outcome, opened_at, closed_at, published_at`). Уникальный индекс гарантирует не больше одного открытого тура на сессию.
- `votes` (`id, round_id → rounds, option_id → options, anonymous_voter_key, is_synthetic, created_at`), `UNIQUE (round_id, anonymous_voter_key)`.
- `final_decisions` (`session_id, winning_option_id, confirmed_at, confirmation_method, source_round_id`).
- `volunteer_ideas` (`id, session_id, idea, contact, created_at`). Связи с голосами нет.
- `access_codes` (`code_hash, session_id`): хранится только HMAC кода.
- `admin_audit_log`: действия организатора, IP только в виде усечённого HMAC.

Триггеры: голос только в открытый тур, только за допущенный вариант, синтетические голоса только в демо, голоса нельзя изменять.

## Анонимность и один голос

- Браузер создаёт 256-битный случайный ключ (`crypto.getRandomValues`) и хранит его в `localStorage`.
- Сервер хранит не ключ, а `HMAC-SHA256(APP_SECRET, session_id + ключ)`. Без секрета сервера сопоставить запись с устройством невозможно.
- Повторная отправка того же выбора с тем же ключом возвращает `accepted, duplicate: true` (идемпотентно). Другой выбор отклоняется как `already_voted`.
- Режим одноразовых кодов: ключом служит HMAC кода. Код работает один раз в каждом туре и не связан с именем.
- Ограничение: в открытом режиме разные браузеры или устройства дают разные ключи. Это указано в README.

## API

Публичные маршруты:

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/current` | slug текущей реальной сессии |
| GET | `/api/sessions/:slug/state` | публичное состояние (без распределения до публикации) |
| GET | `/api/sessions/:slug/stream` | SSE с тем же состоянием |
| POST | `/api/sessions/:slug/vote` | `{roundId, optionId, voterKey \| code}` |
| POST | `/api/sessions/:slug/voted` | в каких турах этот ключ уже голосовал (без раскрытия выбора) |
| POST | `/api/sessions/:slug/check-code` | проверка кода |
| POST | `/api/sessions/:slug/volunteer` | заявка «У меня есть кейс!» (только после решения «эстафета») |

Маршруты организатора (`/api/admin/*`) требуют подписанный httpOnly cookie (`SameSite=Strict`), а изменяющие запросы — ещё и заголовок `X-Veche-Admin: 1` (защита от CSRF). Доступно: сессии, туры (`rounds`, `close`, `publish`), решение, экспорт CSV, коды, демо-голоса, сброс и удаление демо, заявки добровольцев, журнал.

## Безопасность

- Пароль администратора и секреты задаются только переменными окружения сервера. В production без них сервер не стартует.
- Сравнение пароля выполняется за постоянное время. Входов не больше 10 за 15 минут с одного IP.
- Ограничение частоты: голосование — 20 запросов в минуту на ключ и 600 в минуту на IP (весь зал часто выходит в сеть с одного IP).
- Заголовки: CSP `default-src 'self'`, `X-Frame-Options: DENY`, `nosniff`, `no-referrer`, HSTS в production.
- Экспорт CSV не содержит ключей и контактов и защищён от CSV-инъекций.

## Синхронизация

Каждое изменение вызывает `hub.notify(sessionId)`. Подписчики SSE (телефоны, экран зала, админка) получают новое состояние, близкие события объединяются (120 мс). Если SSE недоступен, клиент опрашивает `/state` каждые 3 с и показывает плашку о нестабильной связи. После восстановления сети состояние перечитывается.
